# TorchNeuron public beta (Neuron SDK 2.33.0)

AWS Neuron SDK 2.33.0 introduces TorchNeuron as a public beta. TorchNeuron uses
the PyTorch `PrivateUse1` extension mechanism to add the `neuron` device.

The `torch-neuronx` package supports eager execution, graph compilation, and
custom [NKI](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/index.html)
kernels on Trainium2 and Trainium3.

PyTorch 2.14 support includes eager execution, graph compilation, distributed
execution, caching, core tensor operations, and profiling.

## Compatibility

This release note covers the PyTorch 2.14.0 configuration.

| PyTorch version | `torch-neuronx` package family | Python versions | Platform |
| --- | --- | --- | --- |
| 2.14.0 | 2.14.3.0 | 3.12, 3.13, 3.14 | Linux x86_64 |

See the [installation guide](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/torch/guides/setup-configure-torch-neuronx.html)
for compatible Neuron driver, runtime, compiler, and Python packages.

## Features

### Eager execution

Run supported tensor operations on Neuron while Python controls the
application. Use
[`torch.nn`](https://docs.pytorch.org/docs/2.14/nn.html) modules and
[`torch.autograd`](https://docs.pytorch.org/docs/2.14/autograd.html) through
supported operations.

Tensor and module placement uses the `neuron` device, including
`.to("neuron")`. Use Python control flow, breakpoints, and intermediate tensor
inspection during development.

Supported training workflows use PyTorch loss computation, backward execution,
and optimizers. Inference retains the standard evaluation and gradient
controls.

The Neuron backend integrates with `torch.accelerator` for device discovery and
selection. Use `torch.neuron.synchronize()` to wait for device work to finish.

Eager dispatch can compile and cache per-operation kernels on first use. Later
calls can reuse matching kernels during development.

### Graph compilation

Compile selected functions or modules with
[`torch.compile`](https://docs.pytorch.org/docs/2.14/generated/torch.compile.html).
The surrounding application remains eager.

Use `backend="neuron"` and `dynamic=False` for static-shape compilation. The
backend compiles forward graphs and autograd backward graphs for supported
training operations.

The decorator form and
[`nn.Module.compile`](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Module.html#torch.nn.Module.compile)
provide other ways to select compiled regions. Model parameters and input
tensors must reside on the Neuron device.

The first execution can include compilation time for invoked graphs. A change
to input shapes can require another compilation.

Neuron uses the default compilation mode. Non-default modes produce a warning
and use the default mode. Inductor-specific tuning options do not configure
Neuron. CUDA graph controls do not provide CUDA graph optimizations for Neuron
execution.

### Distributed execution

Use
[`DistributedDataParallel`](https://docs.pytorch.org/docs/2.14/generated/torch.nn.parallel.DistributedDataParallel.html)
(DDP) and
[`fully_shard`](https://docs.pytorch.org/docs/2.14/distributed.fsdp.fully_shard.html#torch.distributed.fsdp.fully_shard)
(FSDP2) through
[`torch.distributed`](https://docs.pytorch.org/docs/2.14/distributed.html)
APIs.

Tensor parallelism and pipeline parallelism use the same APIs. DTensor and
DeviceMesh provide tensor placement and process group structure.

Supported SDPA paths provide context parallelism, including backward execution.
The Neuron process group supports single-node and multi-node execution. Use one
Neuron device for each process.

Native collectives include `all_reduce`, `all_gather`, and `reduce_scatter`.
Point-to-point `send` and `recv` support tensor exchanges between ranks.
Native uneven all-to-all supports variable split sizes with documented
restrictions.

See the [distributed guide](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/torch/guides/torch-distributed.html).

### Caching

TorchNeuron combines in-process compilation caching with a persistent
executable cache. Processes and distributed ranks can reuse matching
executable artifacts through a shared persistent cache directory.

Cache matching includes the workload, target, logical NeuronCore configuration,
compiler version, and compiler options. Changes to the workload or
configuration can require compilation.

Matching artifacts can reduce repeated compilation during development and
later runs.

Use `torch_neuronx.compiler.compile_only()` to prepare compilation artifacts
without device execution. This mode requires the Neuron compiler and the
target-instance configuration.

Compilation without a device also requires `NEURON_RT_FAKE_INSTANCE_TYPE`. It
returns placeholder outputs that cannot validate model results.

See the [compilation guide](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/torch/compile/how-to-compile-without-hardware.html).

### Core tensor operations and NKI kernels

TorchNeuron implements ATen tensor operations. These operations include
elementwise arithmetic, matrix multiplication, reductions, and tensor
indexing.

Supported operations integrate with
[`torch.nn`](https://docs.pytorch.org/docs/2.14/nn.html) and
[`torch.autograd`](https://docs.pytorch.org/docs/2.14/autograd.html) in eager
and compiled execution.

See the [operator reference](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/torch/reference/api/operators.html)
for support by operation, data type, shape, and execution mode. Use
`torch_neuronx.get_fallback_ops()` to inspect recorded fallback operations.

Use the Neuron Kernel Interface to implement custom operations. You can also
use NKI to tune operations that limit model performance. Use profiling to
select operations for tuning.

`torch_neuronx.nki_op` defines a named PyTorch custom operator.
`torch_neuronx.wrap_nki` makes NKI kernel calls visible during graph capture.
These interfaces integrate custom kernels with eager and compiled execution.

Operator registration includes input mutation declarations. Register a
backward formula with
[`torch.library.register_autograd`](https://docs.pytorch.org/docs/2.14/library.html#torch.library.register_autograd)
when the operator needs a backward pass.

Operators that call raw NKI kernels need a suitable `fake_fn` for compile
tracing. This function describes output metadata without kernel execution.

See the [NKI guide](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/torch/guides/how-to-work-with-nki.html).

### Profiling

Use
[`torch.profiler.profile`](https://docs.pytorch.org/docs/2.14/profiler.html#torch.profiler.profile)
with `NeuronConfig`. This configuration collects framework, runtime, and
device traces for Neuron Explorer.

The traces show the relationship between framework operations and recorded
device activity. A `NeuronProfiler` instance exports framework traces beside
Neuron traces for the session.

Optional device-time correlation supports summaries in `key_averages()` for
matching recorded events.

Use `torch_neuronx.memory_summary()` and `torch_neuronx.memory_stats()` to
inspect allocator statistics. The statistics include current and peak values,
allocation counts, and out-of-memory counts.

Allocation history and snapshots can include memory blocks, allocation events,
release events, and recorded Python stack frames. Memory snapshots can
accompany traces from the same process.

`torch_neuronx.empty_cache()` releases cached blocks while it preserves
allocated tensor memory.

See the [profiling guide](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/tools/neuron-explorer/how-to-profile-workload.html)
and the [memory guide](https://awsdocs-neuron.readthedocs-hosted.com/en/latest/torch/reference/guidelines-memory-management.html).

## Getting started

Run this example on a supported Trainium instance after installation.

```python
import torch
import torch_neuronx

model = torch.nn.Linear(16, 8).to("neuron").eval()
inputs = torch.randn(4, 16, device="neuron")

with torch.no_grad():
    eager_output = model(inputs)
    compiled_model = torch.compile(model, backend="neuron", dynamic=False)
    compiled_output = compiled_model(inputs)

print(tuple(eager_output.cpu().shape))
print(tuple(compiled_output.cpu().shape))
```

Each call returns a tensor with shape `(4, 8)`. Eager dispatch can compile and
cache a kernel on first use. The first compiled call can also include
compilation time.

## Experimental and opt-in features

Adaptive eager execution is experimental and off by default. Set
`TORCH_NEURONX_ENABLE_CONCATENATION=1` before you start Python. This setting
lets the backend combine eligible eager operations.

## Known gaps

- **Dynamic shapes.** Graph compilation requires static shapes. Use
  `dynamic=False`. Native dynamic-shape compilation is not supported. A new
  input shape can require another compilation. Use padding or bucketing to
  limit shape variation. Native dynamic-shape support is planned.
- **TorchAO integration.** Integration with
  [TorchAO](https://docs.pytorch.org/ao/stable/index.html) remains under
  development. This integration includes MXFP8 and other composite data types.
  Public support is planned.
- **First-use compilation.** Initial execution can compile kernels and graphs.
  This compilation can increase startup time for large models. Reuse matching
  persistent cache entries to reduce later compilation. Shape, compiler option,
  or target hardware changes can require compilation.
