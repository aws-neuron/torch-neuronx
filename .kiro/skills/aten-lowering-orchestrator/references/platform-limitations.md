# Platform-limitation allowlist

This file is the **single authority** on which skip/xfail *reasons* an agent may
introduce for an op it is lowering. `verify_op_acceptance.py` reads it and sorts
every NEW skip/xfail into one of three outcomes:

1. **Auto-accept (PASS)** — the reason matches an "Allowed reasons" pattern.
2. **REVIEW** — the reason is NOT on the allowlist, but it cites a real existing
   precedent inline (`... precedent: <an existing group reason or nodeid>`). The
   verifier confirms the cited precedent exists in the baseline registry. The op
   is not blocked: the orchestrator opens the DRAFT PR and lists the reason under
   "Xfails needing human sign-off", and a human accepts or rejects it at review.
   This is how a legitimate but unlisted reason lands WITHOUT the agent stopping
   mid-run to ask.
3. **FAIL** — the reason is not on the allowlist and cites no valid precedent, OR
   it matches a "Not allowed" deny pattern. A deny match is ALWAYS a FAIL; a
   precedent citation cannot rescue it.

Rules the verifier enforces:
- A reason must name the concrete capability gap, not the symptom. "Group by root
  cause, not by op name" (repo registry contract).
- Adding a skip/xfail for the op you just implemented is not acceptable unless it
  is a genuine platform limitation.
- When the root cause is fixed, the whole `SkipGroup` is deleted, never edited to
  point at fewer tests.

**Changing this file is a reviewed change** (CODEOWNERS / `pr-review`). An agent
must not widen the allowlist to get an op through. For an unlisted reason, cite a
precedent and let REVIEW route it to a human; do NOT edit this file.

Patterns are matched case-insensitively as regex/substring against the group's
`reason` string.

## Allowed reasons

- `complex dtypes? (not|un)`          — cfloat/cdouble/chalf/complex unsupported on Neuron
- `\bfft\b`                            — FFT family unsupported
- `sparse`                             — sparse layouts/ops not implemented
- `float64|double .*(precision|not|slow to compile|emulation timeout)` — no native float64; precision-floor, unsupported, or fp64-emulation compile-time blowup
- `cuda[- ]specific|cuda graph`        — CUDA-only feature, not applicable to Neuron
- `not implemented: aten::`            — genuine missing dependency op (MUST cite a tracking issue)
- `quantiz`                            — quantized dtype paths unsupported
- `nested tensor|nestedtensor`         — nested tensors unsupported
- `mkldnn|onednn`                      — CPU-backend-specific layout
- `upstream test bug`                  — the upstream test itself is wrong (MUST cite an upstream issue/PR)
- `dtype superset|wider dtype set than aten|aten reference kernel (lacks|does not support)` — Neuron supports more dtypes than aten's OpInfo table claims, because aten's own reference kernel cannot run them (for example `_upsample_bilinear2d_aa` for bf16/fp16). Use this ONLY for a `test_dtypes` divergence from a proven dtype superset. The PR MUST prove each extra dtype bit-close against an fp32/fp64 oracle in a passing unit test. Do NOT use it when Neuron supports FEWER dtypes than aten, or for a wrong value on a dtype aten does claim.
- `out= .*(unsafe[- ]cast|safe[- ]cast guard).*#1862` — the shared `out=` dtype safe-cast guard is not centralized yet (tracked in #1862). Remove this reason when #1862 lands.

Two reasons are deliberately NOT auto-accepted; route them through REVIEW with a
precedent instead (they are too easy to abuse as a blanket "close enough"):
- a native transcendental (exp/sqrt/cos, NOT erf) that misses aten's high-ulp
  `test_reference_numerics_*` oracle — cite the sibling that already xfails it,
  and prove bit-closeness against an fp32/fp64 oracle in a passing unit test.
- a fundamental floating-point precision floor that no dtype recovers (fmod on a
  large dividend) — cite a precedent and attach the fp32/fp64 loss table.

## Not allowed (deny patterns — always FAIL, a precedent cannot rescue them)

These match the group `reason` text. A new xfail whose reason matches one of
these is a hard FAIL even if it cites a precedent. Fix the op instead.

- `tensor-likes are not close|not close|wrong (value|numeric)` — a numeric mismatch on float32/bf16/int is a real defect, not a limitation
- `pure integer|integer[- ]only|fails.*integer dtype` — a failure that reproduces on integer dtypes is a real bug
- `crash|arity|dispatch fail|cpu fallback|falls back to cpu` — the op being lowered must dispatch and run on Neuron
- `layout|stride|non[- ]contiguous` — layout/stride handling bugs must be fixed
- `\bflaky\b` — "flaky" without a root cause is not a reason; investigate, fix, or file and link an issue
- `fewer dtypes` — Neuron supporting fewer dtypes than aten is a real gap, not the dtype-superset case
- `opinfo broken|generic opinfo` — a broken OpInfo is usually a real lowering gap; give a detailed per-op reason
